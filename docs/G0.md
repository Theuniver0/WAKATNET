## 2. Écarts avec le §1 qui touchent la conception (extrait de `docs/LABO.md` §5)

1. **E-FR-1** : FreeRADIUS 3.2.10 et non 3.2.8. Interdire 3.2.9.
2. **E-FR-2, prouvé sur 3.2.5 et confirmé dans le code source de 3.2.8 à 3.2.10** : `require_message_authenticator = yes` dans le bloc client **ne s'applique pas** aux clients dynamiques. Il faut ajouter `&FreeRADIUS-Client-Require-MA = yes` dans le serveur virtuel `dynamic_clients`. Sans cela, T10 échoue : la protection BlastRADIUS serait absente.
3. **L6, prouvé sur 3.2.5** : PostgreSQL arrêté ⇒ l'authentification est **rejetée** (Access-Reject, sans Reply-Message) pour un client en cache. Un client absent du cache ne reçoit aucune réponse. C'est le scénario T13 : la réplique du nœud B est la seule parade. Parade côté serveur prouvée (L6e) : `if (fail) { do_not_respond }` après le module `sql` fait taire le nœud au lieu de rejeter. Reste à prouver sur CHR que RouterOS bascule alors vers B sur timeout (LABO-16) ; si c'est le cas, cette variante devient le choix par défaut, par un ADR.
4. **L4, prouvé** : une révocation en base prend effet au plus après `lifetime` ; une rotation de secret coupe le routeur pendant au plus `lifetime`. Aucun cache négatif : chaque paquet d'une IP inconnue relance une requête SQL (risque de charge à cadrer en phase 2).
5. **E-ROS-12 (probable, critique, non vérifié)** : le walled garden HTTP ne filtrerait pas par nom d'hôte en HTTPS. Si c'est confirmé, toute page de paiement hébergée exige des entrées `walled-garden ip` par adresse : cela renforce le choix d'un flux en API directe (LABO-14).
6. **E12 (tiers, non vérifié)** : PI-SPI serait obligatoire depuis le 02/11/2026 pour la monnaie électronique interopérable, ce qui rendrait « hors v1 » à réexaminer.
7. **§1.5 Concurrence : rien n'a été vérifié.**
